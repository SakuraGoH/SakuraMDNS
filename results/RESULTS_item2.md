# Item 2 — GPU 并行 Potts 采样：实现、校验与「有效样本/秒」对比

日期：2026-11-26　设备：Intel Arc iGPU（Meteor Lake，112 EU，22.6 GB **共享内存**）+ Core Ultra（4P+8E+2LPE）
条件：L=16/32，q=3，β=1.2（有序相，即"前后强关联"的困难情形），J=1

## 1. 结论先说

**在这台机器上，GPU 并行采样全面慢于 CPU 的 C++ Swendsen-Wang**，最优也只有它的 0.44×。

| 配置 | CPU `potts_sw` | GPU `potts_cb` | GPU `potts_wolff` |
|---|---|---|---|
| L=16, B=1024 | **97 225 ESS/s (1.00×)** | 40 033 (0.41×) | 10 958 (0.11×) |
| L=16, B=8192 | **92 048 (1.00×)** | 40 843 (0.44×) | 17 576 (0.19×) |
| L=32, B=1024 | **23 164 (1.00×)** | 9 624 (0.42×) | 2 924 (0.13×) |
| L=32, B=8192 | **23 109 (1.00×)** | 8 085 (0.35×) | 9 359 (0.40×) |

更重要的是一个副产品数字：**用 C++ SW 生成 10 万个有效样本只需约 1 秒**（L=16）。
也就是说 — **数据生成根本不是这个项目的瓶颈**，瓶颈在训练。

## 3. 校验：15/15 通过

**精确枚举**（可穷举的体系）：

```
[PASS] ising_cb      L=4 β=0.4407  TV=0.0039  label_dev=0.0032
[PASS] ising_wolff   L=4 β=0.4407  TV=0.0069  label_dev=0.0058
[PASS] ising_wolff   L=4 β=0.6     TV=0.0019  label_dev=0.0063
[PASS] potts_wolff   L=3 β=1.005   TV=0.0075  label_dev=0.0037
[PASS] potts_wolff   L=3 β=1.2     TV=0.0039  label_dev=0.0037
[PASS] potts_wolff   L=3 β=0.5     TV=0.0081  label_dev=0.0033
```

**与 C++ SW 交叉检验**（L 更大、无法穷举）：TV ≤ 0.015，平均能量差 ≤ 0.0015。

**L=16 平衡性**：全部与 SW 一致（|ΔE| ≤ 0.006）。

### 开发中抓到并修掉的两个真 bug

**bug 1：Wolff 用"每格点一个随机数"激活键 → 分布有偏。**
正确的 Fortuin–Kasteleyn 随机簇模型要求**每条边**独立 Bernoulli。格点若同时邻接 k 个簇内格点，必须得到 k 次连接机会；
只给一次会把簇系统性做小 → 移动退化 → 分布偏无序。
实测 L=4, β=0.4407：平均能量 −17.12（应为 −25.12，SW 给 −25.1），TV=0.376。
改为预生成"右/下"两张键表、左右/上下方向共用同一批键后，TV 降到 0.007。

**bug 2：棋盘更新要求 L 为偶数。**
周期边界下奇数 L 的方格点阵**不是二分图**（(0,0) 与 (0,L−1) 同色却相邻），半扫描内部就互相依赖，更新有偏
（L=3 实测 TV=0.056/0.128）。现在 `run()` 对奇数 L 直接报错并提示改用 Wolff。

### 性能优化：把逐层同步折叠掉

Wolff 的簇由键配置唯一确定，**与遍历顺序无关**，所以可以在一次 host 同步内连续扩展 `hops` 层。
设备同步约 0.3 ms，而每层算术仅约 0.02 ms —— 同步是主要成本。`hops=4` 后 L=16/B=8192 从 17.6k 提到 …（见上表）。

## 4. 为什么 GPU 反而更慢：机制分析

L=16 时每个扫描只有 6.3 M 个元素级运算，但要发 **约 24 次 kernel**（2 个半扫描 × 约 12 个算子）。
实测每次算子 0.25–0.3 ms → **7 ms/扫描**，几乎全是 **XPU 算子派发开销**，算术只占几个百分点。
PyTorch XPU 后端没有算子融合，所以小张量上"并行度"完全用不上。

放大到 L=32/B=8192（8.4 M 元素/算子）后，瓶颈转为**显存带宽**：
Potts 棋盘更新要做 (4,B,L,L,q) 的计数张量，B=8192/L=32/q=3 时单个中间张量就有 **1 亿个 bool**，
每半扫描要写+读数遍，而这块 iGPU 的 22.6 GB 是**与 CPU 共享的系统内存**，带宽还要和 CPU 抢。
所以规模变大也没追上来（0.35–0.44×）。

反观 CPU：C++ SW 每条链的工作集只有 L²·4 B = 1–4 KB，完全落在 L1/L2；4 个 P 核跑满即可达到
150 M–500 M 次格点更新/秒，且没有任何派发开销。

**什么时候 GPU 才可能赢**：① 独显（独立显存带宽）；② 用 Triton 把 24 个算子融成 2–3 个；
③ L ≥ 64 且需要同时跑上万条链。这三条在当前硬件上都不成立。

## 5. 对后续计划的影响（重要）

1. **数据生成用 CPU C++ SW**，不要用 GPU。97 k ESS/s 意味着 10 万有效样本 ≈ 1 s，
   一轮训练需要的样本量在秒级就能造完。
2. **GPU 应该花在训练上**（大矩阵乘、注意力），而不是采样。
3. Item 4/5 的闭环里，"扫描"这一步应当是秒级的轻量环节，闭环的节奏由**训练**决定。
   这直接决定了我接下来把工程量投到 Item 3/6/7（架构与优化器），而不是继续榨 GPU 采样。

## 6. 注意事项

- τ 只统计了**能量**与**序参量幅值**（Potts 用"最大态占比"）。真正最慢的是**有符号磁化强度**，
  它会让局域算法（cb / glauber）的 τ 变大更多，因此表中的 ESS/s 对所有算法都是**乐观上界**；
  但由于它更惩罚局域算法，"CPU SW 胜出"这个结论只会更稳，不会翻转。
- 时间测量取 2 次试验的最优值。这台机器的 iGPU 与 CPU 共享功耗/散热预算，单次测量会有 2–4× 抖动
  （第一次跑 CPU SW 得到 650 扫/s，第二次 310 扫/s）。
- 所有 GPU kernel 都用 `torch.Generator(device='xpu')` 播种，可复现。
