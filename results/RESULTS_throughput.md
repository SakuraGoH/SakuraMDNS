# 如何最大化「有效训练集」的产出速度

日期：2026-11-27　设备：RTX 4080 SUPER（云端，独占）　配置：Potts q=3 L=16 β=1.2，nbt-2（6 块 / 64 通道 / 压缩比 2 / 4 头）

## 1. 指标定义

训练数据是模型自己扫出来的，所以真正该最大化的不是"样本/秒"，而是

```
有效样本/秒 = (扫描样本/秒) × (ESS / 批量)
```

一个样本对梯度的贡献正比于它的重要性权重，而 ESS/N ≈ exp(−Var[log w])。
三者决定这个数：

| 因子 | 由什么决定 | 能否在不动算法的前提下优化 |
|---|---|---|
| 原始产出速率 | scan_batch、每次前向的算子数、是否融合 | ✅ 可以 |
| ESS/批量 | 模型与 π 的接近程度（训练质量） | ❌ 不是吞吐旋钮 |
| 占空比 | `steps_per_round / resample_every` | ✅ 可以 |

## 2. 实测（4080S）

### A. `torch.compile`：唯一的大杠杆

| 前向 @B=1024 | 耗时 | 相对 |
|---|---|---|
| eager + autocast（原路径） | 29.5 ms | 1.00× |
| eager，bf16 权重，关 autocast | 19.5 ms | **1.51×** |
| **compiled，bf16** | **10.2 ms** | **2.89×** |

关掉 autocast 本身就有 1.5×——因为 `torch.amp.autocast` 在每次前向里都要进出一个上下文，
而模型只有 96 K 参数，这部分开销占比很高。

### B. 加大 `scan_batch`：无效，甚至更差

| batch | 扫描耗时 | 样本/秒 | ms/样本 |
|---|---|---|---|
| 1024 | 15.3 s | **66.7** | 15.0 |
| 2048 | 34.4 s | 59.5 | 16.8 |
| 4096 | 67.5 s | 60.7 | 16.5 |

每样本成本随 batch 不变甚至变差 ⇒ 单卡上"堆 batch"没有收益。

### C. 多进程并发扫描：几乎不线性

| 并发数 K | 墙钟 | 样本 | 样本/秒 | 相对 K=1 |
|---|---|---|---|---|
| 1 | 21.3 s | 2 048 | 96.2 | 1.00× |
| 2 | 37.3 s | 4 096 | 109.9 | **1.14×** |
| 4 | 70.8 s | 8 192 | 115.7 | **1.20×** |

GPU 已经 ~98% 忙，多进程只是时间片轮转；那 14–20% 来自填补 kernel 之间的空隙。

### D. compile 落地后的端到端效果

| | scan/次 | 一轮（9 次扫描 + 200 步） |
|---|---|---|
| eager | 6.8 s | 88.6 s |
| `--compile` | 4.5 s | **68.0 s（1.30×）** |

scan 只提速 1.51× 而非 2.89×，因为 `scan` 每次迭代还有 256 次 Python 层循环开销（gumbel 采样、
索引、原地写回），这部分不随编译缩小。

按生产配置（24 次扫描 + 600 训练步）折算：

| | 扫描 | 训练 | 轮时 | 样本/秒 |
|---|---|---|---|---|
| 现在 | 178.6 s | 82.8 s | ~262 s | **94** |
| `--compile` | 108 s | 82.8 s | **~191 s** | **~129（+37%）** |

## 3. 对「样本定量训练 + 多线程分摊」设想的评估

把这个设想拆成三条，逐条对照上面的测量：

| 设想 | 实测结论 |
|---|---|
| ① 把样本量均摊到多个线程/进程并行生产 | **只有 1.2×**（K=4）。GPU 是独占瓶颈，线程多少不改变它 |
| ② 随数据累积逐步释放线程 | 这是 **CPU 密集**任务的负载均衡思路。这里被占满的是 GPU 的 kernel 队列，释放 CPU 线程不会让 GPU 变快 |
| ③ 先攒够定量样本再开始训练（解耦两阶段） | **反而更慢**。等价于 `resample_every = steps_per_round`，实测 every=50 只有 71 样本/秒，而 every=25 是 94——因为训练时 GPU 在算但不产样本，两阶段串行 → 总时间 = 扫描 + 训练 |

**核心原因**：生产和训练吃的是**同一块 GPU**。解耦只有在两者能用**不同资源**（不同卡、或 GPU+CPU）时才有收益。

### 那这个设想在什么条件下成立

- **多卡**：每卡一个 worker 独立产样本、汇总后训练 → 接近线性扩展。这时"定量分摊 + 释放"就是标准的并行采样池，设计是对的。
- **异构分工**：比如小批量扫描放 GPU、训练放 CPU（或 NPU），才能真正并行。
- 单卡上唯一能拿到的那点并行收益，就是实测的 ~20% 空隙填充，不值得引入进程池 + 权重同步 + 样本 IPC 的复杂度。

## 4. 推荐的优化顺序

| 优先级 | 手段 | 实测/预期 | 代价 |
|---|---|---|---|
| 1 | **`--compile`**（已实现，commit 69b57bb） | **+37%** 样本/秒 | 一个开关 |
| 2 | 编译**训练**前向（下一步） | 训练从 82.8 s → ~40 s，整轮 ~148 s，**+77%** | 需要把 autocast 移到 loss 外层，风险中等 |
| 3 | `--resample-every 10` | +24%（与 compile 可叠加） | 一个参数 |
| 4 | 多卡并行采样池（你的设想） | 接近线性 | 工程量大，仅多卡时值得 |
| ✗ | 加大 batch / 单卡多进程 | ≤1.2× | 不建议 |

## 5. 复现

```bash
# 单卡并行度、batch、compile 的三合一基准（约 5 分钟）
python scripts/bench_parallel_scan.py --compile --batches 1024,2048,4096 --workers 1,2,4

# 端到端 A/B（各 1 轮）
python scripts/run_closed_loop.py --arch nbt-2 --n-blocks 6 --L 16 --q 3 --rounds 1 \
    --steps-per-round 200 --resample-every 25 --scan-batch 1024 \
    --beta 1.2 --beta-start 1.2 --no-anneal --out-dir runs/ab_eager
python scripts/run_closed_loop.py ... --compile --out-dir runs/ab_compiled
```
